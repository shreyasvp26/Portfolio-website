## The problem

Melanoma survival depends heavily on how early the lesion is looked at, and the practical bottleneck is often not diagnosis but triage — the gap between a person noticing a mole and a dermatologist ever seeing it. Dermoscopic image classification is a well-studied problem with a good public dataset in HAM10000, which makes it a genuinely useful place to learn how a deep-learning model behaves once you have to *deploy* it rather than just report a validation number.

I want to be precise about scope, because medical ML attracts overclaiming. OncoScan is not a diagnostic tool and I am not qualified to build one. It is a screening demonstrator, and the interesting engineering turned out to have very little to do with squeezing out accuracy.

### Why it was built

OncoScan started from exploring skin cancer detection via deep transfer learning on dermoscopic images. Beyond training offline classifiers on the HAM10000 dataset, I wanted to understand the engineering constraints of actually deploying a multimodal medical-adjacent model behind a live public API — cold-start latency, container memory budgets, fail-safe startup checks, and honest scope communication.

## Architecture and technical decisions

The system is deliberately boring: a React single-page app on Vercel, and a FastAPI service that owns the model. The one non-obvious modelling choice is that the network consumes patient metadata alongside the image.

Age and sex are real clinical priors — the base rate of malignancy differs meaningfully across them — so a model that sees only pixels is discarding free signal. A 1280-dimensional image embedding is concatenated with a 128-dimensional metadata embedding and passed to a small fusion classifier.

I collect anatomical site and skin tone in the form but do **not** feed them to the model, and the README says so explicitly. Half-implemented inputs that silently do nothing are how ML demos become misleading, so I'd rather document the gap than hide it behind a form field.

## Technologies used

- **Python & PyTorch:** Multimodal inference pipeline combining an EfficientNet-B0 dermoscopic image backbone (`1280-d`) with a patient-metadata MLP (`128-d`) into a `1408-d` fused classifier trained on HAM10000.
- **FastAPI:** Inference service exposing `POST /predict` with image size and file-type validation plus `/health` model-status reporting.
- **React & Vite:** Frontend upload and metadata intake form with mandatory screening disclaimers, hosted on **Vercel**.

## Engineering challenges and trade-offs

**The trade-off I care most about is the one I lost on paper.** I trained a weighted ensemble of EfficientNet-B1 and B4, DenseNet121, and ResNet50, and it reached roughly 92% classification accuracy — higher than any single backbone I tried. It is also the version I chose not to ship.

Four backbones means four sets of weights to load, four forward passes per image, and a memory footprint that does not fit comfortably in a free-tier container. On a cold start, users would wait through multi-hundred-megabyte model loading before their first result. A single EfficientNet-B0 with metadata fusion gave up a small amount of accuracy and bought back cold-start time, memory headroom, and a deployment I can actually keep running at zero cost.

For a *screening triage demonstrator* whose entire value proposition is "a person can try this in ten seconds", a model nobody waits around for is worth more than a model with a better confusion matrix. If this were a clinical decision-support system with a real infrastructure budget and a regulatory pathway, I would ship the ensemble and the reasoning would invert completely. The right answer depended on the deployment constraints, not on the leaderboard.

<Callout tone="warn" title="Verifiability gap I'm closing">
The ensemble experiment currently lives in a local notebook that is not in the repository, so the ~92% figure is not independently checkable — which by my own standard means you shouldn't take my word for it. The deployed single-backbone model, its weights contract, and its documented limitations are all in the repo. I'm pushing the ensemble training notebook so the comparison is reproducible.
</Callout>

**The threshold is the honest weak point.** A binary classifier behind a sigmoid needs a decision threshold, and mine defaults to `0.5` because that is the arithmetic default — not because anyone validated it. In a screening context the cost of a false negative and a false positive are wildly asymmetric: telling someone their melanoma looks benign is far worse than sending them for an unnecessary check. The correct threshold is therefore almost certainly not `0.5`, and choosing it properly requires a validation set and a stated tolerance for missed positives.

I made the threshold an environment variable rather than a constant so it can be recalibrated without a code change, and I documented in the README that it has not been calibrated. Performance across Fitzpatrick skin-tone types is also unvalidated, which is a well-documented fairness failure mode in dermatology datasets and one I can't claim to have solved.

**Grad-CAM is disabled in the current release.** I had heatmap explainability working during development, but the version that survived into the deployed build produced attribution maps I wasn't confident were faithful, and a misleading heatmap over a medical image is worse than no heatmap — it manufactures trust. It's off until I can verify it.

## Results and measurable outcomes

- **Multimodal feature fusion:** Produces a concatenated **1408-dimensional** representation (`1280-d` EfficientNet-B0 image features + `128-d` metadata MLP output) rather than discarding age and sex clinical priors.
- **Live public deployment:** Accessible end-to-end as a React SPA on Vercel connected to the FastAPI inference API, complete with user-facing non-clinical disclaimers before showing results.
- **Operational safeguards:** Backend refuses startup on missing or mismatched weights, exposes a `/health` endpoint reporting loaded model state, validates weights via script, and keeps `CLASSIFICATION_THRESHOLD` environment-configurable (`0.5` default, explicitly documented as clinically uncalibrated).
- **Documented limitations:** The repository README includes an explicit four-item Known Limitations section and intentionally keeps Grad-CAM disabled until attribution faithfulness is verified.
